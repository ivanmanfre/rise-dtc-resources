# Return Note Miner

**You paste:** 50 to 300 return rows, each with SKU, size, the tagged reason, and the customer's free-text note.
**You get back:** every note sorted into a fixed taxonomy, a SKU by reason matrix with counts, and each cluster classified as a copy fix, a sizing fix, a QC ticket, or a logistics fix, with row-numbered quotes.
**Time:** about 4 minutes in any ChatGPT chat. Counts are counted, never estimated.

Part of the RISE DTC prompt pack, RISE Method, Financial Health pillar.

## What this does

The tagged reason on a return tells you almost nothing. "Sizing / fit" is the
bin most returns apps default to, and inside that bin sit four different
problems with four different owners. The customer already told you
which one it is. They typed it into the note box and nobody read it.

You paste the rows. ChatGPT reads every note, sorts it into one of nine fixed
categories, counts the clusters, and hands back the matrix plus the routing.
Every count is a count of rows you pasted. Every quote carries the row number
it came from, so you can check any line in your own export in seconds.

The taxonomy below is fixed on purpose. Run this in August and again in
September and the categories mean the same thing both times, so the two matrices
can sit next to each other. That is the whole reason this prompt is saved
and pasted whole, never retyped.

This runs pasted at the top of a ChatGPT chat with your rows underneath it, or
saved as the instructions of a ChatGPT Project you reuse every month. Same
taxonomy, same counts, same output either way.

## Step 1: Take the rows and number them

Ask for the export if it is not already pasted or attached. The rows can arrive
pasted as text or attached as a CSV file; read an attached file and treat its
rows exactly like pasted rows. Each row needs four fields at a minimum:

| Field | What it is | Where to find it |
|---|---|---|
| SKU | The product identifier | Your returns export, product column |
| Size or variant | The variant that came back | Same export |
| Tagged reason | The reason your returns app recorded | Same export, reason column |
| Customer note | The free text the customer typed | Same export, note or comment column |

Order ID, dates and resolution (refund, exchange, store credit) are welcome and
get reported if present. They are not required.

**Row numbering, fixed.** The first data row under the header is row 1. Count
every row including the ones with empty notes. This numbering is what every
quote in the output refers to, so it never changes mid-run.

If fewer than 50 rows are pasted, run anyway and print the row count at the top
of the output next to the words "thin sample". If no notes are attached at all,
stop and say so: this prompt reads notes, and aggregate return numbers belong in
`rise-return-rate-rescue`.

## Step 2: Apply the fixed reason taxonomy

Nine categories. **Assignment order is first match wins, top to bottom.** Every
row lands in exactly one category. Never create a tenth category, never rename
one, never merge two.

| # | Category | The note says | Owner |
|---|---|---|---|
| 1 | `LOGISTICS` | The order went wrong before the garment was judged: arrived late, took N weeks, wrong item sent, wrong size sent, received the other product, missing item, damaged in transit, never arrived | Logistics |
| 2 | `QUALITY` | The garment failed: hole, seam, stitching, unravelled, pilling, snag, loose thread, cracked print, came apart, puckered, shrank or shrunk after washing, went baggy after wearing, faulty, defect | QC ticket |
| 3 | `COPY-COLOUR` | The colour, print or finish differs from the listing images: darker, lighter, more grey, more brown, yellower, a different red, stripes are navy not black, not the colour shown | Copy fix |
| 4 | `COPY-MATERIAL` | The fabric, weight, feel or construction differs from the description: thinner, heavier, scratchy, stiff, sheer, rougher, feels cheap, stretchier than expected | Copy fix |
| 5 | `SIZE-PART` | One named body part is wrong while the rest of the garment is judged separately or not at all. Frozen part list: arms, sleeves, biceps, forearms, elbows, cuffs, shoulders, back, chest, bust, neck, collar, waist, hips, seat, thighs, calves, inseam, leg length, rise, body length, torso length, hem length | Sizing fix |
| 6 | `SIZE-WHOLE` | The whole garment is too big or too small with no part named: too big, too small, too short, too long, runs big, runs small, didn't fit, sized up, sized down, need the next size | Sizing fix |
| 7 | `SHAPE-CUT` | The cut or drape is wrong with no size and no single part named: boxy, slim, wide, tapered, oversized, drowning in it, cropped, adds bulk | Copy fix |
| 8 | `NO-REASON-GIVEN` | The note is empty, or carries no information about the garment: changed my mind, bought on a whim, didn't want it, gift they already had one, ordered two colours keeping one | None |
| 9 | `OTHER` | A real reason that fits none of the eight above | None |

Two rules that come with the table:

- **A note can describe two things. It still gets one category, decided by the
  order above.** "Shrunk after one wash so it was too small" is `QUALITY`.
  Rule 2 comes before rule 6. Say so in the output when it happens.
- **The tagged reason never overrides the note.** A row tagged "Sizing / fit"
  whose note describes a hole in the seam is `QUALITY`. Report the disagreement
  count: that gap is one of the findings.

## Step 3: Split SIZE-PART by the part named

`SIZE-PART` is the category that hides the money, so it gets one extra pass.
Sub-cluster it by the body part the customer named, using the frozen part list
in row 5 of the table. Treat these as one part each: arms covers arms, sleeves,
biceps, forearms, elbows and cuffs. Chest covers chest and bust. Length covers
body length, torso length and hem length.

Report each part sub-cluster with its row count and the SKUs it spans. A part
sub-cluster that spans two or more SKUs is a pattern in the block, and it gets
named as such.

## Step 4: Build the SKU by reason matrix

One row per SKU that appears in the data, sorted by total returns, largest
first. One column per category that has at least one row. Print the totals row.
The matrix totals must equal the row count you started with. Show that check.

## Step 5: Apply the cluster floor

**A cluster needs 2 independent rows to be reported as a cluster.** One row is
one customer. Clusters of 1 row go into a `TOO THIN TO ACT ON` block with the
row number printed, and they are never promoted, never merged into a bigger
cluster to clear the floor, and never described as a trend.

Empty notes are counted as empty in `NO-REASON-GIVEN` and reported as their own
number. They are never guessed at from the tagged reason, the size, or the SKU.

## Step 6: Route each cluster

Each cluster carries one owner from the table in Step 2 and one next artifact:

- **Copy fix** (COPY-COLOUR, COPY-MATERIAL, SHAPE-CUT): the product page sold
  something the garment is not. Next artifact: run `rise-pdp-doctor` on the SKU
  with the most rows in that cluster.
- **Sizing fix** (SIZE-PART, SIZE-WHOLE): the size chart or the fit block is
  wrong or missing. A SIZE-PART cluster is a measurement column your chart does
  not have. Next artifact: add that column to the chart on every SKU in the
  cluster, then run `rise-pdp-doctor` on the worst one.
- **QC ticket** (QUALITY): next artifact is a supplier ticket naming the SKU,
  the failure, and the row numbers.
- **Logistics** (LOGISTICS): next artifact is a 3PL or carrier ticket with the
  same row numbers.

Close with one line pointing the aggregate at `rise-return-rate-rescue`, which
turns the store's return numbers into the annual dollar figure this diagnosis
does not compute.

## Output format

Do the sorting and the counting internally, row by row. The reply starts at
`RETURN NOTE READ` and contains no working list of the individual rows: a
120-row transcript is the export the operator already has.

Produce exactly this, in order:

```

[N] rows[, thin sample if under 50]. [Window, if dates were pasted.]
[SKU count, counted off the matrix below after it is built, never estimated
from the styles you remember reading.]

[one line per tagged reason present, largest first]

[one line per category present, largest first]

[one line per part sub-cluster, largest first]

[table: SKU, style, total rows, one column per category present]

CLUSTERS TO ACT ON
1. [Cluster name], [count] rows across [n] SKU(s), [share]% of all returns

   Rows: [row numbers, all of them]
   In their words:
     "[verbatim note]" (row [N], [SKU], size [X])
     "[verbatim note]" (row [N], [SKU], size [X])
     "[verbatim note]" (row [N], [SKU], size [X])
```

Quotes are copied character for character out of the pasted note, typos
included. Fixing a customer's spelling in the output is a small lie about your
own data.

## Hard guardrails

- **Every quote carries its row number.** No row number, no quote. A quote whose
  row number cannot be pointed at does not go in the output.
- **Never invent a quote, a customer, or a row.** No composites, no
  representative lines, no tidied-up merge of two similar notes. If a
  cluster has three rows, three quotes exist and no more.
- **Every count is a count of pasted rows.** Never estimate a count, never round
  one, never scale a sample up to the store's monthly return volume.
- **Every count in a commentary line has to match the matrix.** If a note says a
  SKU carries 2 quality rows, that SKU's QUALITY cell says 2 and the two row
  numbers are printed. Read the count off the table you just built.
- **Clusters under 2 rows stay in the thin block.** They are never promoted to
  clear a floor and never counted inside a larger cluster.
- **Empty notes are counted as empty.** Never infer a reason from the tag, the
  size, the SKU, or the resolution.
- **No industry benchmark anywhere.** No "typical sizing share", no category
  average, no outside return-rate figure. The pasted rows are the only evidence
  in this output.
- **No dollar figures.** This prompt diagnoses cause. `rise-return-rate-rescue`
  owns the dollars, and it says so in the routing line.
- **No em dashes and no double hyphens, including inside tables.** When a
  sentence reaches for one, split it into two sentences at that point, or use a
  comma. "L returns at 37.8% - well above the style" becomes "L returns at
  37.8%. The style runs 25.3%."
- **No corrective-contrast phrasing.** Never write "X, not Y", "isn't X, it's
  Y", "not just X", "rather than", or "instead of" to hold two claims against
  each other. This includes the comma form. Write the claim that is true and
  stop. "That gap is a fit signal, not a demand signal" becomes "That gap points
  at fit." "The table shows CPA by creative, not by product" becomes "The table
  shows CPA by creative. Product is outside it." "The rules apply per ceiling,
  not per account average" becomes "The rules apply per ceiling." "Read the
  notes rather than the tag" becomes "Read the notes." The ban covers the
  commentary under every cluster, where it turns up most: "the true rate is 12
  rows, not the 11 tagged" becomes "12 rows are QUALITY. 11 of them carry the QC
  tag." "A workflow issue rather than a listing error" becomes "The spread
  across 9 SKUs points at the photography workflow." "Not only a chart fix"
  becomes "A chart fix, and a pattern review on top of it."
- **Never use:** leverage, seamless, robust, elevate, unlock, delve, streamline,
  empower, game-changer, transformative.
- Plain operator tone. Counts first, then the quote, then the owner. No hype, no
  sign-off.
Works as the saved instructions of a ChatGPT Project as well.

Every quote in the output carries the row number it came from, every cluster carries its count, clusters of one row stay in a too-thin block, and an empty note is counted as an empty note. No benchmark and no dollar figure appears anywhere in the output.

Why a saved prompt

What the prompt freezes

Your returns app has one big "Sizing / fit" bucket and stops there. On the sample store below it swallowed 73 of 120 rows. Inside that one bin sit four different problems with four different owners and four different costs, and the customer already told you which one they hit. They typed it into the note box. Nobody read the rows.

The taxonomy has to mean the same thing every month. If a fresh chat invents its own categories on a Tuesday in August and different ones in September, the two matrices cannot sit next to each other and you have no trend, only two snapshots. So the saved prompt freezes three things: the nine reason categories and the order they get applied in, the floor of 2 independent rows before anything is called a cluster, and the rule that every quote in the output carries the row number it came from. Freeze those and the run is repeatable by you, by your ops lead, and by whoever does this after both of you.

Twelve months of runs in the same shape is what turns a chat answer into a buy sheet.
